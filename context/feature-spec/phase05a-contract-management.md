## 1. Goal

Implement persistent Contract history linked to Employees. Authorized HR users
must be able to create, inspect, update, and list Contracts while PostgreSQL
prevents overlapping terms for the same Employee. Each Contract records the
period-specific department, job position, monthly wage, Salary Structure, and
optional Working Schedule override needed by future payroll.

This phase does not create Payruns or calculate salary.

## 3. Scope

### In scope

- Contract PostgreSQL model, migration, relations, and indexes.
- Database and service-level prevention of overlapping Employee Contract ranges.
- Server-generated immutable Contract numbers.
- Contract list, detail, create, and update APIs.
- Derived `Running` / `Expired` display status.
- Contract-to-Employee, Department, Salary Structure, and optional Schedule links.
- Contract and schedule-resolution helpers from Phase 5B integrated into services.
- Contract list/detail/create/edit frontend connected to real APIs.
- Employee smart-button Contract count and filtered navigation.
- Append-only audit events for Contract creation and updates.
- Representative idempotent Contract seed data.

### Out of scope

- Hard deletion or a DELETE endpoint.
- A manually editable Contract status.
- Contract splitting inside one payroll Period.
- Payrun, Payslip, Attendance, or Time Off models.
- Salary calculation, tax, compliance, probation, benefits, attachments, or e-signature.
- Multiple companies, currencies, or wage frequencies.
- Employee count changes on Salary Structure screens beyond a real derived count.

## 4. Locked Business Decisions

1. One Employee may have many historical Contracts, but their inclusive date
   ranges must never overlap.
2. `startDate` and `endDate` are business dates. `endDate` is nullable for an
   open-ended Contract and is inclusive when present.
3. Contract status is not stored:
   - `Expired` when `endDate < today`;
   - `Running` otherwise, including a future-dated Contract.
   The dates remain visible so a future Contract is not mistaken for currently
   effective. Do not introduce an `Upcoming` label because canonical vocabulary
   permits only `Running` and `Expired`.
4. Ending a Contract means setting its `endDate`; history is never removed.
5. Payroll later resolves exactly one Contract satisfying:

   ```text
   startDate <= periodStart
   AND (endDate IS NULL OR endDate >= periodEnd)
   ```

6. A Contract must cover the entire payroll Period. Mid-period Contract
   splitting is out of scope.
7. The Contract stores its own Department and job position. Default them from
   the selected Employee in create mode, but allow an authorized user to change
   them. This preserves period-specific employment history.
8. Monthly wage is non-negative Decimal and crosses HTTP as a string.
9. Every Contract requires a Salary Structure.
10. A Contract schedule is optional. Downstream schedule precedence is:

    ```text
    Contract.workingScheduleId -> Employee.workingScheduleId -> missing
    ```

11. Creation and relationship changes may select only active Employee,
    Department, Working Schedule, and Salary Structure records. Existing
    Contracts retain references if a related record is later made inactive.
12. Contract number is generated by the server and cannot be edited.
13. Contract `departmentId`, `jobPosition`, `wage`, `salaryStructureId`, dates,
    and schedule are authoritative; do not read these values dynamically from
    the current Employee when showing an existing Contract.
14. The frontend never decides whether date ranges overlap. It may provide an
    early warning, but the API and PostgreSQL constraint are authoritative.
15. Dates are submitted and returned as `YYYY-MM-DD`; do not serialize them as
    local-midnight JavaScript timestamps.

## 5. Prisma Schema and Migration

Add to `apps/api/prisma/schema.prisma`:

```prisma
model Contract {
  id                  String   @id @default(uuid())
  contractNumber      String   @unique
  employeeId          String
  departmentId        String
  workingScheduleId   String?
  salaryStructureId   String
  jobPosition         String
  startDate           DateTime @db.Date
  endDate             DateTime? @db.Date
  monthlyWage         Decimal  @db.Decimal(18, 2)
  notes               String?
  createdAt           DateTime @default(now()) @db.Timestamptz(3)
  updatedAt           DateTime @updatedAt @db.Timestamptz(3)

  employee        Employee        @relation(fields: [employeeId], references: [id], onDelete: Restrict)
  department      Department      @relation(fields: [departmentId], references: [id], onDelete: Restrict)
  workingSchedule WorkingSchedule? @relation(fields: [workingScheduleId], references: [id], onDelete: Restrict)
  salaryStructure SalaryStructure @relation(fields: [salaryStructureId], references: [id], onDelete: Restrict)

  @@index([employeeId, startDate, endDate])
  @@index([departmentId])
  @@index([workingScheduleId])
  @@index([salaryStructureId])
  @@index([endDate])
}
```

Add the inverse `contracts` relation to Employee, Department,
WorkingSchedule, and SalaryStructure.

Migration name:

```text
phase05_contract_management
```

Customize the generated SQL:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE SEQUENCE IF NOT EXISTS contract_number_seq START 1;

ALTER TABLE "Contract"
  ADD CONSTRAINT "Contract_contractNumber_check"
    CHECK ("contractNumber" ~ '^CON/[0-9]{4}/[0-9]{6}$'),
  ADD CONSTRAINT "Contract_jobPosition_check"
    CHECK (length(btrim("jobPosition")) BETWEEN 2 AND 100),
  ADD CONSTRAINT "Contract_monthlyWage_check"
    CHECK ("monthlyWage" >= 0),
  ADD CONSTRAINT "Contract_dates_check"
    CHECK ("endDate" IS NULL OR "endDate" >= "startDate"),
  ADD CONSTRAINT "Contract_notes_check"
    CHECK ("notes" IS NULL OR length(btrim("notes")) BETWEEN 1 AND 1000),
  ADD CONSTRAINT "Contract_employee_dates_excl"
    EXCLUDE USING gist (
      "employeeId" WITH =,
      daterange(
        "startDate",
        COALESCE("endDate" + 1, 'infinity'::date),
        '[)'
      ) WITH &&
    );
```

The exclusion range converts the inclusive `endDate` to an exclusive upper
bound. Therefore `2026-01-01..2026-01-31` may be followed by a Contract that
starts `2026-02-01`, but not one that starts `2026-01-31`.

Generate a number inside the create transaction:

```text
CON/<startDate year>/<nextval(contract_number_seq), padded to 6 digits>
```

Sequence gaps after rolled-back transactions are acceptable. Never calculate
the next number with `count + 1` or `max + 1`.

## 6. Shared Contracts and Validation

Create `packages/shared/src/types/contracts.ts` and export it from the shared
barrel.

```ts
export const ContractStatusValues = ['RUNNING', 'EXPIRED'] as const;
export type ContractStatus = (typeof ContractStatusValues)[number];

export interface ContractInput {
  employeeId: string;
  departmentId: string;
  workingScheduleId: string | null;
  salaryStructureId: string;
  jobPosition: string;
  startDate: string;
  endDate: string | null;
  monthlyWage: string;
  notes: string | null;
}
```

Validation rules:

- All IDs are non-empty UUID strings.
- `jobPosition`: trim, 2-100 characters.
- dates: real calendar dates in exact `YYYY-MM-DD` format.
- `endDate` is null or greater than/equal to `startDate`.
- `monthlyWage`: canonical non-negative decimal string, at most 16 integral
  digits and 2 fractional digits. Reject commas, currency symbols, exponent
  notation, `NaN`, and JSON numbers.
- `notes`: null or trimmed 1-1000 characters. Empty input normalizes to null.
- Client input must not contain `id`, `contractNumber`, `status`, timestamps,
  relation names, or derived values.

Required `ContractListItemDto` fields:

- id, contractNumber;
- Employee summary: id, employeeNumber, fullName;
- Department summary: id, name;
- startDate, endDate, monthlyWage, currency;
- jobPosition;
- Salary Structure summary: id, name, status;
- Working Schedule summary or null;
- `effectiveScheduleSource`: `CONTRACT`, `EMPLOYEE`, or `MISSING`;
- `effectiveSchedule` summary or null;
- derived status;
- `isEffectiveToday` boolean;
- createdAt and updatedAt.

Detail DTO adds `notes` and current Employee-default Department, job position,
and Schedule summaries only as form suggestions. It must clearly distinguish
those suggestions from persisted Contract values.

All Decimal fields remain strings in DTOs.

## 7. Status and Date Handling

Create one backend mapper/helper for derived status:

```ts
status = endDate !== null && endDate < today ? 'EXPIRED' : 'RUNNING'
isEffectiveToday = startDate <= today && (endDate === null || endDate >= today)
```

- `today` is the company business date, currently UTC because no company
  timezone setting exists.
- Accept an injected `today` in tests; do not freeze module state at startup.
- Use date-only comparison. Do not compare locale-formatted strings.
- A future Contract returns `RUNNING` with `isEffectiveToday: false`.
- APIs must support a status filter using these derived semantics.

## 8. Authorization

| Capability | Employee | HR Manager | HR Payroll User | HR Payroll Manager | Admin |
| --- | --- | --- | --- | --- | --- |
| Global Contract list/detail | Deny | Read | Read | Read | Read |
| Own Contract list/detail | Read | Read | Read | Read | Read |
| Create/update Contract | Deny | Write | Write | Write | Write |
| Hard delete | Deny | Deny | Deny | Deny | Deny |

Rules:

- Employee access must be restricted to Contracts whose `employeeId` equals
  the Employee linked to the authenticated User Account.
- Unlinked Employee-role users receive `EMPLOYEE_PROFILE_NOT_LINKED`.
- Query parameters cannot bypass ownership.
- Salary Structure remains read-only for HR Payroll User, but selecting an
  existing active Structure on a Contract is allowed because Contract CRUD is
  an HR permission.

## 9. API Contract

Mount under `/api/v1/contracts`.

### `GET /api/v1/contracts`

Query parameters:

```text
search
employeeId
departmentId
salaryStructureId
status=RUNNING|EXPIRED
effectiveOn=YYYY-MM-DD
page=1
pageSize=20 (max 100)
sort=contractNumber|employee|startDate|endDate|monthlyWage|status
order=asc|desc
```

Behavior:

- Search Contract number, Employee number/name, and job position.
- `effectiveOn` keeps Contracts whose range contains that date.
- Employee role ignores/rejects another `employeeId` and sees own rows only.
- Default sort: `startDate desc, contractNumber desc, id asc`.
- Pagination must be stable and include total count.
- Status filtering is based on the same request-scoped UTC `today` used in DTOs.

### `GET /api/v1/contracts/:id`

Return full Contract detail with persisted relationship summaries and effective
Schedule information. Return 404 for missing or unauthorized Employee-owned
records; do not reveal another Employee's Contract existence.

### `POST /api/v1/contracts`

Accept `ContractInput`, generate Contract number, create in one transaction,
append `CONTRACT_CREATED` AuditLog, and return 201.

Pre-write validation:

1. Employee exists and is active.
2. Department exists and is active.
3. Salary Structure exists and is active with a valid active-rule graph.
4. Optional Working Schedule exists and is active.
5. Dates and wage are valid.
6. No existing Contract for the Employee overlaps the inclusive range.

The PostgreSQL exclusion constraint remains authoritative for races.

### `PUT /api/v1/contracts/:id`

Use full replacement semantics with `ContractInput`.

- Contract number is immutable.
- Apply active-reference checks only when a reference is changed; an unrelated
  update must not fail merely because an existing referenced record became
  inactive.
- Recheck overlap while excluding the current Contract ID.
- Append `CONTRACT_UPDATED` with safe before/after JSON in the same transaction.
- Return the updated detail DTO.

### Supporting selectors

Reuse existing paginated Employee, Department, Working Schedule, and Salary
Structure endpoints. Add lightweight selector endpoints only if the existing
ones cannot provide ID, display label, and active status; do not duplicate
domain APIs inside Contracts.

### Salary Structure Contract count

After Contract exists, Structure list/detail DTOs may expose
`employeeCount` as the distinct count of Employees with at least one Contract
referencing that Structure. It must be a real database result, never a constant.

## 10. Public Errors

Use the standard API envelope and these stable codes:

| HTTP | Code | Meaning |
| ---: | --- | --- |
| 400 | `INVALID_CONTRACT_INPUT` | Body or query validation failed |
| 400 | `INVALID_CONTRACT_PERIOD` | End is before start or date format is invalid |
| 401 | existing auth code | Not signed in |
| 403 | `CONTRACT_ACCESS_DENIED` | Role cannot perform operation |
| 404 | `CONTRACT_NOT_FOUND` | Missing or ownership-hidden Contract |
| 409 | `CONTRACT_NUMBER_CONFLICT` | Generated number collided unexpectedly |
| 409 | `CONTRACT_PERIOD_OVERLAP` | Employee has an overlapping Contract |
| 422 | `CONTRACT_EMPLOYEE_INACTIVE` | Selected Employee is inactive |
| 422 | `CONTRACT_DEPARTMENT_INACTIVE` | Selected Department is inactive |
| 422 | `CONTRACT_SCHEDULE_INACTIVE` | Selected Schedule is inactive |
| 422 | `CONTRACT_STRUCTURE_INACTIVE` | Selected Structure is inactive |
| 422 | `CONTRACT_STRUCTURE_INVALID` | Active Structure configuration is unusable |

Field errors belong in `error.fields`. Never expose constraint names, Prisma
codes, SQL text, IDs from inaccessible records, or stack traces.

## 14. Seed Data

Extend the seed in foreign-key-safe order after Employees, Departments,
Schedules, and Salary Structures.

Create representative idempotent data:

- one Employee with an expired historical Contract and a non-overlapping
  current/open-ended Contract;
- one Contract using an explicit Schedule override;
- one Contract using the Employee default Schedule;
- all Contracts reference the seeded Regular Salary Structure.

Upsert by fixed IDs or Contract numbers. Seed ranges must never overlap and
rerunning seed must not consume new Contract sequence values unnecessarily.

## 15. Automated Tests

### Persistence and integrity

- migration applies on a clean test database;
- direct database insert rejects end before start;
- direct inserts reject overlapping closed, open-ended, containing, contained,
  and same-day ranges;
- adjacent inclusive ranges are accepted;
- overlapping create/update requests return `CONTRACT_PERIOD_OVERLAP`;
- concurrent overlapping creates produce one success and one safe conflict;
- Decimal wage round-trips exactly as a string;
- Contract number is unique, formatted, generated safely, and immutable.

### API and RBAC

- unauthenticated requests return 401;
- four HR/Admin roles can list/read/create/update;
- Employee sees only own Contracts and cannot mutate;
- unlinked Employee receives the existing profile-link error;
- inactive or missing relationship targets are rejected on create;
- unchanged inactive historical references do not block an unrelated update;
- list search, filters, derived status, effective date, sorting, and pagination
  are correct and stable;
- no DELETE route exists;
- AuditLog is created atomically with each successful mutation and never for a
  rejected mutation.

### Integration and regression

- Phase 5B resolver is used for full-period Contract selection;
- Schedule precedence returns Contract override, then Employee default;
- Structure count is derived from Contract data;
- Employee Contract smart count/filter uses IDs and real data;
- all auth, Schedule, Employee, and Salary Configuration tests still pass.

## 19. Non-Negotiables

- Do not store a manually editable or cron-dependent status.
- Do not allow overlapping inclusive ranges for one Employee.
- Do not resolve a Contract that covers only part of a Period.
- Do not use Employee's current department/job/schedule as the persisted
  historical Contract terms.
- Do not default silently to another Salary Structure.
- Do not use JavaScript `number` for wage.
- Do not accept client-generated Contract numbers.
- Do not hard-delete Contracts or expose DELETE.
- Do not create Payroll, Attendance, or Time Off models in this phase.
